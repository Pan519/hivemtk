# ADR-019 多租户的边界：监管、内容审核、LLM 池并发、非 UI 链路隔离与数据面路由

- **状态**：Accepted（现状陈述 + P3 演进口径）
- **决策日期**：2026-10-11
- **回答的问题**：多租户目的是什么；监管与内容审核在租户隔离下如何做；LLM 池下游业务侧并发怎么治理；reach 工具链/追踪/hooks 这些天然丢租户标记的场景怎么办；数据库怎么隔离；请求怎么路由。

---

## 1. 多租户的目的

**一句话：让"一个部署实例服务多个互不信任的团队"成立，且不为此牺牲平台方的运营与监管能力。**

拆开是三个目标，缺一不可：

1. **数据不串**（保密面）：团队 A 的客户/会话/线索对 B 不可见——P0 已交付（team_id 行级隔离 + JWT scope 注入 + 服务端强制过滤，见 ADR-017 与 docs/multi-tenant-rbac-saas-plan.md）。
2. **资源不抢**（公平面）：一个团队的用量不能挤占别人的推理/发送配额——本期交付订阅配额（MaxUsers/MaxMessagesMonthly），LLM 池并发治理见 §3。
3. **平台可管**（监管面）：平台方要能越过隔离看到一切、审计一切、下线任何内容——这是很多"隔离实现"漏掉的反向能力，见 §2。

隔离是手段，**可运营的多租户 SaaS** 才是目的。

## 2. 监管与内容审核：隔离是"抽屉"，监管是"万能钥匙 + 账本"

**原则：租户隔离给用户的是抽屉，给平台的必须是总钥匙。两者不矛盾，靠三层实现：**

### 2.1 平台管理员跨租户直通（已交付）
`role=admin` 在 scope 层直通（`TeamScoped` 三态语义），可查改全量数据——这是**有意的后门，且全量审计**（操作留 operation_logs，管理动作留 mcp_credential_audit_logs）。监管者不必破坏隔离设计，他站在隔离层之上。

### 2.2 内容审核管线（P3 交付口径）
- **审核队列独立于租户**：`content_moderation` 表记录 `team_id + 内容引用 + 审核状态`，审核员（新角色 `moderator`，platform 侧）按队列消费，**不因 team_id 过滤而看不到待审内容**——审核读路径显式走 `ModerationScope`（越过 team 过滤的专用 scope，仅 moderator/admin 角色可达，且每次访问留痕）。
- **机审在先**：reach.send / knowledge.add_doc / inbox 出站三条写入路径挂机审钩子（敏感词/模型分类器），命中即进人工队列并**阻断外发**；不命中的照发但留 `moderation=auto-passed` 标记（事后可抽查）。
- **下线即全租户生效**：内容被判定违规 → 按内容 ID 全局下线（消息撤回走既有 recall 链路），`team_id` 只影响"该团队谁还能看到这条记录的元数据"，不影响下线动作的执行范围。
- **举报不跨租户泄露**：用户举报只提交内容引用（ID + 摘要哈希），审核员在审核态下才解引用——举报通道本身不构成跨租户读取面。

### 2.3 监管报表（P3）
平台侧聚合视图（各团队用量/违规率/审计异常），读路径走平台直通，写路径只读副本——不与租户查询争抢主库。

## 3. LLM 池的下游业务侧并发治理

**现状**：LLM provider 池是全局共享的（dispatcher 按场景路由 provider），多租户后所有团队的请求混在一个池里——先到的团队可以占满并发，把别人饿死。

**口径：池不按租户物理切分（那是反 SaaS 的），按"加权公平队列 + 双层配额"逻辑切分：**

1. **租户级令牌桶**（P3，dispatcher 入口）：
   - 每团队一个令牌桶（容量 = 订阅方案的并发数 `max_concurrency`，速率 = `rpm_limit`）；
   - 桶空时请求**不失败而是排队**（有界队列，超时 429 + Retry-After），内部调用方（SOP 管线）降速，外部调用方（MCP/开放 API）收到明确限流错误；
   - 未订阅团队共享一个"默认桶"（低配），防裸奔。
2. **平台级保底**：每团队保底 1 并发（防饿死），总量池按 provider 真实容量配置，桶只是分群治理。
3. **成本归账**：dispatcher 的 usage 记录带上 team_id（LLMRoutingLog 加列），月末按团队出账——计费系统的 `BillingRecord` 直接消费（组合计费里的 per_seat 之外的用量计费档）。
4. **热点隔离**：单团队突发（跑批）不影响他人的关键是**队列有界**——排队深度超阈值直接 429，绝不无界堆积拖垮 provider 池。

实现落点：`internal/aiagent/llm/dispatcher.go` 的 Dispatch 入口加 `TenantRateLimiter`（golang.org/x/time/rate 的多桶封装），LLMRoutingLog 加 team_id 列，配额数字从团队订阅方案读。

## 4. 非 UI 链路"天然丢租户标记"的场景与对策

**问题本质**：Web 请求有 JWT，租户标记随 ctx 全程可用；但 reach 工具链（定时管线）、追踪系统（trace 采集）、hooks（事件订阅回调）、bridge/ingest（消息入口）这些链路的起点**没有用户请求**——ctx 里没有团队身份。

**解法不是"在这些链路里补登录"，而是让租户标记跟着"数据"走而不是跟着"请求"走：**

### 4.1 标记的三个携带层（已交付/交付中）
| 层 | 机制 | 状态 |
|---|---|---|
| 数据层（根本） | 业务行自带 `team_id` 列，Create 回调自动回填（`scope.FillTeamIDOnCreate`）——行一旦落库，归属永不丢失 | ✅ P0 |
| 消息层 | 出站消息（reach/outbox）构造时从目标客户/会话行取 team_id 写进消息体 `extra.team_id` | ✅ P0（随行数据） |
| 上下文层 | 定时任务/管线以"服务上下文"运行（无身份=系统直通），但触达的**目标选择**（客户圈选）已经过 team 过滤——管线拿到的就是本租户的数据集 | ✅ P0 |

### 4.2 各链路逐个说
- **reach 工具链**：管线由租户配置触发 → 配置行有 team_id → 圈人查询带 `TeamScoped` → 产出的触达任务行被 Create 回填 team_id → 外发记录可归属。**风险点**：定时器本体无租户（这是对的——定时器是平台设施），审计上以"配置归属团队"追溯。✅ 已闭环
- **追踪系统（trace）**：trace 是平台诊断数据，**设计上不隔离**（平台排障需要全量），但每条 trace 元数据带 team_id（TraceMiddleware 从 JWT ctx 取；非 UI 链路从处理的业务行取）——排障时可按团队过滤，但平时全量可见。口径：**诊断面归平台，业务面归租户**。✅ 口径明确
- **hooks（事件回调）**：出站 webhook 的 payload 带 `team_id` 字段（消费方自证来源）；入站回调（渠道 webhook）从**渠道账号归属**解析团队（channel → account → team），解析不出=进平台侧死信队列，不落任何团队。📋 P3 补 payload 字段与渠道归属解析
- **bridge/ingest**：消息入口按**渠道账号**解析团队（`CustomerChannel.team_id`，P3 加列）——消息永远落在"这个渠道号属于哪个团队"的团队里，不依赖请求方自报。📋 P3（当前消息靠 Create 回调落默认团队，多账号混跑时需要渠道归属列才能正确分流）

### 4.3 一条铁律
**任何"平台机器流量"创建的业务行必须可归属**：要么从触发的配置/目标数据继承 team_id，要么显式落默认团队并被回填钩子归队——绝不接受"team 0 的业务行"长期存在（guard 已在启动日志喊这种漂移）。

## 5. 数据库隔离

**口径：共享库 + 行级隔离（已交付），单租户物理库是 P3 的"大客户选项"，不是默认。**

| 方案 | 现状 | 何时升级 |
|---|---|---|
| **共享库行级**（当前） | 全部业务表带 team_id，scope 强制过滤 | 默认，中小规模（≤几百团队）够用 |
| **schema-per-tenant** | 不做——迁移/运维成本乘 N，pgvector 等扩展管理噩梦 | 不采纳（除非强合规客户单独谈） |
| **database-per-tenant** | P3 选项：连接串按 team 路由（GORM DBResolver + team→shard 映射表），大客户/独立备份诉求时启用 | 有付费大客户且明确要求物理隔离时 |

行级隔离的正确性由三道闸保证（均已交付）：CI 棘轮门禁（新裸查询必须带 scope）+ 启动回填幂等（无 team 0 业务行漂移）+ fail-closed 语义（漏注入身份=少看不是多看）。

## 6. 请求路由

**两层含义，分开回答：**

### 6.1 租户→数据面的路由（现在）
单库阶段没有"路由"——路由就是 SQL 的 WHERE 子句。ctx 里的 team_id 由 **JWT 中间件**（Web 请求）/ **owner 继承**（MCP 调用）/ **服务上下文回填**（管线）三种入口写入，之后全程随 `context.Context` 传递。数据库层无感知。

### 6.2 未来分库时的路由（P3 预留）
- **路由键 = JWT 里的 team_id**（所有入口都解析它，包括 MCP guard——这是为什么凭证绑定账户是 P0 交付的一部分）；
- **路由点 = GORM 插件层**（DBResolver 注册 team→connection 映射，`scope.TeamScoped` 之外再拦一层"连接选择"）——业务代码零改动；
- **平台管理员跨库查询**：admin 的全量直通在分库后变为**扇出聚合**（逐库查询合并），只用于平台报表/监管，普通路径永不扇出；
- **迁移工具**：team_id 已让数据天然可分片（按 team_id 导出/导入即可搬库）——这是行级隔离先行的红利。

### 6.3 LLM/渠道等外部资源的路由
见 §3（令牌桶按团队分桶）与渠道账号归属（§4.2 hooks）——外部资源的"路由"本质是**配额与归属**，不是网络寻址。

---

## 结论（一页话）

多租户 = **行级隔离给用户抽屉 + 平台总钥匙给自己**。监管靠"平台直通 + 独立审核队列 + 全量审计"，不做租户间的监管让步。LLM 池不物理切分，用租户令牌桶做加权公平 + 用量归账。非 UI 链路靠**数据自携带 team_id**（行级列 + 回调回填）而不是请求凭证，管线/追踪/hooks 各有明确归属口径。数据库共享库行级隔离是默认正确答案，database-per-tenant 只是 P3 的大客户选项——而今天的 team_id 列正是明天分库的路由键。已交付的 P0/P1/P2 是这个蓝图的隔离与账户地基；§2.2/§3/§4.2 标 📋 的部分为 P3 演进项，落地顺序按付费与合规压力排。
